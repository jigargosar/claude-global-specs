Here's a tight plan. One upfront decision drives everything: **short-lived access token + refresh token** (recommended) vs. a single long-lived token. I'll assume the former since it's the standard secure default — say the word if you want the simpler single-token version.

## Plan

- **Dependencies & config** — `jsonwebtoken`, `bcrypt` (password hashing). Put `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, and TTLs in env (never commit). Fail fast at boot if secrets are missing.
- **Token service** — small module: `signAccess` (~15min TTL), `signRefresh` (~7day TTL), `verify`. Include minimal claims (`sub`, `role`), not sensitive data.
- **Auth routes** — `POST /register` (hash password), `POST /login` (verify → issue both tokens), `POST /refresh` (validate refresh → new access token), `POST /logout` (invalidate refresh).
- **Middleware** — `requireAuth` reads `Authorization: Bearer`, verifies access token, attaches `req.user`; returns 401 on failure. Optional `requireRole` for authorization.
- **Refresh token storage** — persist a hash of refresh tokens (or a jti) server-side so logout/rotation works; rotate on each refresh. This is the piece people skip and then can't revoke.
- **Transport** — access token in memory/Authorization header; refresh token in an `httpOnly`, `Secure`, `SameSite` cookie to reduce XSS exposure.
- **Error handling & hardening** — consistent 401/403 responses, rate-limit login, generic auth errors (don't leak which field was wrong).

**Key decisions to confirm:**
1. Access+refresh (recommended) or single token?
2. User store — what DB are you on? (affects register/login and refresh storage)
3. Web browser client (favor cookie for refresh) or mobile/API client (header is fine)?

Answer those three and I'll implement against your actual stack.
