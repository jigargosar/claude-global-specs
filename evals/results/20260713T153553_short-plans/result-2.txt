## JWT auth plan (Node/Express)

**Setup**
- Add deps: `jsonwebtoken`, `bcrypt` (password hashing), and a validator (`zod` or `express-validator`).
- Store `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, and TTLs in env (never hardcode). Fail fast on boot if missing.

**Core pieces**
- **User store**: users table/collection with a `passwordHash` (bcrypt, cost ~12). Registration hashes; login compares.
- **Token service**: `signAccess` (~15 min) and `signRefresh` (~7 days), plus verify helpers. Keep signing/verifying in one module so config lives in one place.
- **Auth routes**: `POST /register`, `POST /login` (issues both tokens), `POST /refresh` (rotates and reissues), `POST /logout` (revokes refresh token).
- **Auth middleware**: reads `Authorization: Bearer <token>`, verifies the access token, attaches `req.user`, returns 401 on failure. Apply to protected routes.

**Hardening (do these, not optional)**
- Generic error messages on login (don't reveal which field was wrong); rate-limit `/login` and `/refresh`.
- Refresh-token rotation + a revocation store (denylist or per-user token version) so logout/compromise actually invalidates.

**Two decisions that change the code — pick before I start:**
1. **Token transport**: `Authorization` header (simplest, good for pure APIs/mobile) vs **httpOnly cookies** (safer against XSS but needs CSRF protection). Default I'd take: header for an API, unless a browser SPA shares the origin.
2. **Refresh strategy**: stateless access-only (simplest, but no server-side logout) vs access+refresh with a revocation store (what I outlined above). Default: access+refresh.
