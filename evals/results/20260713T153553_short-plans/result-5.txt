## Plan

- **Dependencies**: `jsonwebtoken` for signing/verifying, `bcrypt` (or `argon2`) for password hashing. Put `JWT_SECRET` (or an RSA keypair) and token TTLs in env, never in code.
- **Token strategy** — *key decision*: short-lived access token (~15 min) + long-lived refresh token (~7 days), vs. a single access token. Refresh flow is more work but lets you revoke/rotate; single-token is simpler but you can't invalidate before expiry. I'd default to the two-token approach.
- **Auth endpoints**: `POST /register` (hash + store user), `POST /login` (verify password → issue tokens), `POST /refresh` (validate refresh token → new access token), `POST /logout` (invalidate refresh token).
- **Middleware**: `authenticate` — pull token from `Authorization: Bearer`, `jwt.verify`, attach `req.user`, return 401 on failure. Optionally a `requireRole` middleware layered on top for authorization.
- **Token delivery** — *key decision*: return access token in JSON body (client stores in memory) and refresh token in an `httpOnly`, `Secure`, `SameSite` cookie. Avoid `localStorage` for anything (XSS-exposed). If this is a pure service-to-service API, cookies may not apply — say so.
- **Refresh token persistence**: store a hash of the refresh token (or a `tokenVersion`/`jti` per user) in the DB so logout and rotation can actually revoke. Stateless access tokens stay unrevoked until expiry — accept that or add a short TTL.
- **Hardening**: rate-limit `/login`, generic error messages (don't leak which of user/pass was wrong), validate input, HTTPS only, rotate refresh tokens on each use.

Two things that change the details:

1. **What's your data layer** (Postgres/Prisma, Mongo/Mongoose, something else)? Determines how I write the user model and refresh-token storage.
2. **Browser client or service-to-service?** Decides cookies-vs-header for the refresh token.

Answer those and I'll write it to match your stack. If you'd rather I just pick sensible defaults (Postgres + Prisma, browser client, two-token flow), say go.
