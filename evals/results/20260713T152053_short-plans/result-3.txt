## JWT auth plan

**Token model** — Short-lived access token (~15 min, stateless, sent as `Authorization: Bearer`) + long-lived refresh token (~7–30 days, stored server-side so it can be revoked). This is the main decision: pure stateless JWT is simpler but you can't revoke; the refresh-token-with-server-store hybrid is the sensible default.

- **Deps**: `jsonwebtoken` (sign/verify), `bcrypt` (password hashing), `zod` (validate request bodies). Secrets (`JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`) from env, never committed.
- **Endpoints**: `POST /auth/register`, `POST /auth/login` (returns access + refresh), `POST /auth/refresh` (rotate refresh token, issue new access), `POST /auth/logout` (invalidate stored refresh token).
- **Password handling**: `bcrypt.hash` on register (cost ~12), `bcrypt.compare` on login. Never store or log plaintext.
- **Auth middleware**: verify access token, attach `req.user`, return 401 on missing/expired/invalid. Optional role/scope check as a second middleware for protected routes.
- **Refresh storage**: persist refresh tokens (hashed) per user/session with expiry; rotate on each refresh and revoke the old one so a stolen token can't be reused.
- **Transport**: prefer sending refresh token as an `httpOnly`, `Secure`, `SameSite` cookie (mitigates XSS token theft); access token in the response body/memory. If you're API-only for mobile, body is fine.

**Decisions I'd default to unless you say otherwise**: access+refresh hybrid (not pure stateless), refresh token in httpOnly cookie, bcrypt over argon2 for ecosystem simplicity.

Two things that change the plan — is this a **browser SPA or mobile/service client** (drives cookie vs. body for the refresh token), and do you already have a **user store / DB** picked (drives where refresh tokens live)? Tell me and I'll firm it up, then write code.
