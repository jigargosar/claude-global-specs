## Plan

- **Token model**: short-lived access token (~15 min) + longer refresh token (~7 days). Refresh flow lets you revoke sessions without making access tokens long-lived. *Decision: skip refresh tokens if this is a simple internal API — one access token is simpler.*
- **Storage/transport**: `httpOnly` `Secure` `SameSite` cookies if a browser is the client (protects against XSS token theft); `Authorization: Bearer` header if it's a mobile/service client. *Decision: who's the client? This drives cookie-vs-header and CSRF handling.*
- **Secrets**: sign with `RS256` (or `HS256` for a single service) using a key from env/secret manager — never hardcoded. Access and refresh tokens use distinct secrets.
- **Endpoints**: `POST /auth/register`, `POST /auth/login` (bcrypt/argon2 password verify → issue tokens), `POST /auth/refresh`, `POST /auth/logout`.
- **Middleware**: `requireAuth` verifies signature + expiry, attaches `req.user`; returns 401 on failure. Optional role/scope check layered on top.
- **Revocation**: refresh tokens stored server-side (DB/Redis) so logout and "log out everywhere" actually invalidate; access tokens stay stateless.
- **Hardening**: rate-limit login, validate inputs, generic error messages (no user-enumeration), rotate refresh tokens on use.

## Library choice
`jsonwebtoken` for signing/verifying, `bcrypt` or `argon2` for passwords. If you're open to a batteries-included option, `jose` is a modern alternative with better key handling.

2. **Refresh tokens** — want revocable sessions, or is a single short access token enough?
